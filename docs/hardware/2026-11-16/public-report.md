# ZCU102 PS-only hardware validation

Test: Live PS-only software and operating-system gate for v4.0.0-zcu102.1-rc1, on the installed board after the separately performed hostname/LLMNR customization. Overall: limited PS-only validation; corrected device discovery PASS, allocation NOT passed (unloaded-overlay prerequisite), reboot NOT tested.

How: Verified laptop name resolution against the known endpoint before numeric-address SSH. Initial SSH selected the installed virtual-environment interpreter without sourcing either profile script. The corrected run executed the revised accompanying script as root in a fresh Python process after sourcing both scripts, exactly:

```sh
sudo bash -c 'source /etc/profile.d/xrt_setup.sh && source /etc/profile.d/pynq_venv.sh && python hardware_smoke.py'
```

The test script was temporarily staged under /tmp for execution and removed in finally. It asserts the environment and expected versions, emits JSON, and exits nonzero on a failed check. Corrected observed exit status: 1; stderr empty. In the prior run, authenticated to Jupyter, created one owned kernel, checked execute_reply=ok and idle plus an explicit completion marker, and deleted that kernel in finally. Read kernel/service logs, device tree, storage and DRM driver links. No overlay was loaded.

Results: aarch64, Linux 6.12.40-xilinx-g0900176227cc, Python 3.12.3, PYNQ 4.0.0 and NumPy 1.26.4. Deterministic matrix sum 510720 passed in SSH and Jupyter. Both required Metadata/Utils direct_url commit pins matched. MemTotal 4016972 KiB, CMA 524288 KiB, swap 524284 KiB support the stock 4 GiB configuration. SD effective capacity 15931539456 bytes; root partition 15822470656 bytes and ext4 filesystem 15467515904 bytes. resizefs journal records success. Machine ID is nonempty and three SSH host private-key files exist; contents and unique identities were not exported.

The zocl module is loaded. card1 and renderD128 bind to zocl-drm; card0 binds to the display subsystem. FPGA-manager read-only state is unknown. Independently attempted 1024 and 262144 uint32 allocations (4096 bytes and 1 MiB), serially: SSH reports `RuntimeError: No Devices Found` for both sizes; the owned Jupyter kernel reports `RuntimeError: Overlay is not downloaded` for both sizes. These are preserved initial observations. Corrected SSH reports XRT environment present=true, registered device count=1, type=EmbeddedDevice. Both 4096-byte and 1048576-byte probes report exactly `RuntimeError: Overlay is not downloaded`. Thus fill/sync/compare did not run; allocation is NOT passed. Finally frees any successfully created buffer. Prior authenticated Jupyter math PASS is retained without a rerun; no persistent environment was changed.

Primary source checked on the installed pinned PYNQ: `pl_server/__init__.py` imports EmbeddedDevice only when XILINX_XRT is set before import. The installed XRT profile script exports that variable and updates PATH. `EmbeddedDevice.default_memory` (lines 566-573) requires overlay memory metadata or existing global state and otherwise raises the observed exception. The initial SSH No Devices Found is therefore a test-environment finding, not evidence of a bad image. With no loaded overlay, the corrected exception is the expected PS-only prerequisite; it does not prove a broken driver. No overlay download or synthetic mem_dict was used.

Zero failed systemd units and Jupyter active. Exact relevant kernel messages: `zocl-drm axi:zyxclmm_drm: error -ENXIO: IRQ index 8 not found` and `[drm] Failed to initialize the cma mem reserved nodes`. These warnings remain literal independent observations; their causal relationship to allocation is unproven. Additional observed errors include AES and SHA3 probe error -95 and missing regulatory.db error -2. No services were disabled. Device tree declares PS UART0 console, ZynqMP UART compatibility, RGMII-ID, TI PHY compatibility ethernet-phy-id2000.a231 and PS reference clock 33330000 Hz; kernel identifies TI DP83867. These are declarations/driver observations, not instrument measurements. DT model says ZCU102 Rev1.0; physical revision and exact silicon part were not independently read.

Conclusion: Booted PS software, resized root, dependencies, memory configuration and authenticated Jupyter execution are demonstrated. PYNQ allocation readiness is NOT demonstrated and the full gate does not pass. Module/device presence alone is insufficient. Reboot was skipped because an existing serial-console login was observed, despite zero pre-existing Jupyter kernels or sessions. No persistence-after-reboot claim is made.

Limits / ways to resolve: Use both profile scripts before a fresh PYNQ import for SSH. Allocation requires an approved overlay/memory-metadata prerequisite test outside this PS-only scope. Investigate kernel warnings independently before attributing cause; no configuration, packages or source were changed to force a pass. Reboot and persistence remain not tested; the existing console login was respected. Prior clean-image flash/full-readback/boot evidence is supplied provenance and was not repeated in this run; the live installed board includes later hostname/LLMNR changes absent from the release image. Board clock dates are not trusted as test timestamps. No PL, GPIO, DMA, FMC, video, PL DDR, RF, or clock-instrument functionality was tested. Other boards and serial ports were untouched. Owned kernel deleted, no buffer remains allocated, no COM port opened, temporary board scripts removed. Repository publication remains with the parent.
